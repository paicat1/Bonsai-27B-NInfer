## 二、测速口径（必读）

- **客户端流式计时**：`decode_tok_s = (completion_tokens - 1) / (last_chunk_t - first_chunk_t)`，首 token 归 prefill，不计入 decode 分母
- **greedy（temperature=0）为主口径**，输出完全确定、可复现（同请求多轮数字逐位一致）
- thinking 关闭（`enable_thinking=false`），排除思考 token 干扰
- 每档预热 2 次（GPU idle 时钟陷阱，方案文档 §M6 要求）+ 正式 3–7 次取中位数
- prompt：中文"秋天图书馆的午后短文" / 英文"history of computing essay"，输出 256 token
- **环境为非独占 GPU**：LM Studio.exe（GUI 挂机）+ Edge/桌面进程共存，显存 11.5–11.8GB/16GB；实测偶发一次 54.7 t/s 离群值（判定为后台瞬时干扰），剔除后 7 样本中位 67.6 t/s
- TTFT：99–150ms（裸/投机档均同量级）

## 三、各档明细

### 3.1 裸 decode（无 --spec）— PASS

- 7 个正式样本（zh T=0.7 + zh T=0 + zh 补测）：54.7–68.4 t/s，中位 **67.6**；剔除离群后稳定 66–68
- 英文 T=0：65.3–67.7，中位 **66.3**
- 结论：decode 速度与语言无关（符合预期），**5080 实测超过论文 4090 档 ≥60 t/s 判据**
- 启动账本：weights 6.70 GiB，KV 32K bf16（pages 512/512，runtime 2.46 GiB，free 5.48 GiB）

### 3.2 MTP K=2 — 机制生效，净收益 ≈0

- zh T=0：65.3 t/s；en T=0：68.1 t/s —— **均与裸档打平（无加速）**
- 草稿接受率：zh T=0.7 32–44%（波动），**T=0 确定性 44.0%**（81/184，5 轮逐位一致）；en T=0 **45.9%**（122/266）
- 与论文差距：接受率 44–46% vs 论文 59.4%（差 ~14pp）
- **每步账目**（en，256 token）：133 验证步 × 28.2ms/步 = 3.75s；裸档 14.7ms/token。MTP 每步成本 ≈ 裸跑 2 token 成本，每步产出 1.93 token → 1.93/2.0 ≈ 0.97x，即打平
- 日志口径交叉验证：serve 端 `decode 65.7 tok/s` 与客户端 65.3 一致，口径吻合

### 3.3 DFlash2 K=7 — 英文 1.58x 正收益，中文负收益

- **启动缺陷**：默认参数启动即崩（详见第四节）；加 `--lm-head-draft` 后成功
- zh T=0：62.0 t/s，接受率 **5.4%**（52/959，5 轮逐位一致）
- en T=0：**104.7 t/s**（105.1% 上限内的 1.58x vs 裸 66.3），接受率 **21.1%**（151/716，3 轮逐位一致）
- 中英接受率差 4 倍：与 DFlash 草稿域（131072 候选域 Q4 头）偏英文/代码训练分布的画像一致
- 启动账本：weights 9.10 GiB（裸 6.70 + DFlash2 草稿/候选头 2.40），runtime 2.97 GiB，free 2.59 GiB
- 注意：K=7 为论文推荐值；K 曲线（1–15）未扫，后续可选实验

## 四、发现与缺陷

### 4.1【P1-功能缺陷】DFlash2 默认（Full 头）启动崩溃 — 根因已定位，修复方案待批

- 症状：`--spec dflash2 --draft-tokens 7` 启动 → `FATAL server failed during startup | linear_topk: unsupported head profile`（preparing CUDA graphs 阶段）
- **根因（2026-10-06 更正，据第三方审核报告 §5.3 + TELE 源码复核）**：**`linear_topk` 的 head profile 白名单不含三元(PQ2_0)**。
  - `linear_topk.cpp:37-51 resolve_profile` 全档白名单**只接受三种**（实测逐行）：`(kLinearTopKFullRows, W8G32_F16S)`、`(kLinearTopKFullRows, FP8_E4M3FN_ROW_BF16S)`、`(kLinearTopKOptimizedRows, Q4G64_F16S)`；**全文件 grep `PQ2|PTQ1|ternary` = 零命中**。
  - 而 Bonsai 制品输出头**就是折叠三元**（`bindings.cpp:629` `text/output_head` = PQ2_0；`layouts_impl.h:404-411` 注释即铁证）⇒ `resolve_profile(PQ2_0_G128, 248320, 5120)` **无 case 命中** ⇒ `linear_topk.cpp:50` 抛 "unsupported head profile"。
  - ⚠️ **原表述"248077 ≠ 248320 行数错位"作废**：`resolve_profile` 收的是 **`head.n`（本就是 248320）**；`248077` 是 `valid_rows`（契约规定值，`include/ninfer/ops/linear_topk.h:28/39` 明写），`dflash_impl.h:317` 传它**符合契约、调用正确**——两者从未在同一比较里相遇。
- 定性（更正）：**上游 head profile 白名单未注册三元格式**（非"行数错位"）；Full 组合在 sm_89 参考树上同样会炸，不是 sm_120a 移植特有
- 旁证：`--spec dflash`（一代）被正确拒绝（`layouts_impl.h:714`，27B target 只编译了 DFlash2：`config.h:77`），属设计行为非缺陷
- 修复选项（**等用户裁决，未动任何代码**）：
  - A1：`dflash_impl.h:317` 改传 `output_rows`（248320）——**经代码核查不可行**：卡点是 `qtype` 不在白名单；改 `valid_rows` 只会让 `:245` 的 `valid_rows != kLinearTopKFullValidRows` 校验失败（报错变为 "invalid full-head profile or valid_rows"），且按契约真会把 245 行 padding 纳入 top-k（原担忧方向对、原因错）。
  - A2：`linear_topk.cpp` resolve_profile 放宽 Full 档为 `head_rows ≤ 248320`——**经代码核查不可行**：放宽行数范围不会让 PQ2_0 命中（卡点是 qtype）。
  - A3：不修代码，文档记录"DFlash2 必须加 `--lm-head-draft`"——**唯一可行且已采用的选项**（走 131072 行 Q4 Optimized 头，`dflash_impl.h:321`）
  - （未列）注册三元 `linear_topk` profile：真正的代码级修法，但等于新增 head profile + kernel 路径，成本高；且中文接受率 5.4%，收益前景差。
- 可观测性改进（零风险，建议）：`linear_topk.cpp` Full 分派处当 `qtype` 非 W8/FP8 时，抛带格式名的消息（如 `no profile for the output-head format (PQ2_0_G128); use the optimized proposal head`），替代笼统的 "unsupported head profile"
- M4 期"--spec dflash2 可用"的验证仅到 CLI 参数层，端到端启动为本次首次实测——又一例"参数全绿 ≠ 端到端可用"

### 4.2【性能发现】MTP/DFlash2 每步成本未摊薄（与论文画像不符）

- 论文 4090 上 MTP K=2 = 96.7–130.8 t/s（裸 60+ 的 1.6–2.2x）；本构建实测 1.0x
- 结构性原因（推测，超出本轮验证范围）：每验证步 wall time ≈ 裸 2 token，说明 draft 前向 + 3-token 批验证的成本 ≈ 2 次完整前向；可能涉及 sm_89 路径在 120a 上的 kernel 调优缺口（kTargetSmCount 等仅对齐 SM 数，不保证每 kernel 最优）
- 不影响正确性（M5 PPL 已盖章），纯性能议题

### 4.3【用户问答题】"共享 GPU 内存 9G"的解释 — 不影响速度

- 来源：引擎启动时锁定 **9.15 GiB host pinned 内存**（`pinning host state 1.15 GiB` + `pinning host KV 8.00 GiB`，三档日志一致），即 CPU 侧 8 份上下文状态 × 1GiB KV 池（日志 `context cache | host 8 states, 8.00 GiB KV`）
- Windows 任务管理器把 GPU 可 DMA 访问的系统内存计入"共享 GPU 内存"，故显示 ~9G
- **不影响 decode 速度的数学证明**：68 t/s × 6.7GB 权重 ≈ 每秒 ~100GB 读需求 > PCIe 4.0 x16 实际 ~30GB/s 上限——若热路径在共享内存，物理上不可能跑出 68 t/s；显存账本（weights 6.7 + KV + runtime = 11.5 ≈ 专用 11.8G 观察值）自洽
- 实际代价：锁页内存不可换出，占用 ~9.2GB 系统内存
- 这是引擎设计行为（host 侧上下文池，长对话换入换出/锚点用），不是异常卸载

### 4.4【深挖追加】每步成本模型与 K=1 判决实验（同日第二轮，回答"为什么草稿模式差"）

**每步成本账本**（全部实测，多源交叉吻合：客户端计时 = serve 日志 decode = 产出/每步反推）：

| 配置 | 接受率(T=0) | 产出/步 | 每步时间 | 吞吐 | vs 裸 |
|------|------------|---------|----------|------|-------|
| 裸 | — | 1.00 | 14.7ms | 68.0 | 1.00x |
| MTP K=1 | 54.4% | 1.55 | 21.4ms | **72.0** | **1.06x** |
| MTP K=2 | 44.0% | 1.92 | 28.2ms | 68.1 | 1.00x |
| MTP K=2 + 小头 | 40.1% | 1.79 | 28.3ms | 62.9 | 0.92x |
| DFlash2 K=7 (en) | 21.1% | 2.50 | 23.4ms | 104.7 | 1.58x |
| DFlash2 K=7 (zh) | 5.4% | 1.38 | 21.9ms | 62.0 | 0.91x |

**三个判决性实验**：

1. **MTP K=1（判决实验）**：72.0 t/s（71.0–80.4），接受率 54.4%（56/103，逐位一致）——**首次正收益**。每步 21.4ms vs 裸 14.7ms → 投机链固定开销 ≈ 6.7ms/步；K=1→K=2 边际 ~7ms/draft 而边际产出仅 0.37 token → **由赚转亏的临界点在 K=1 与 K=2 之间**。K≥2 全部白干。
2. **--lm-head-draft 证伪实验（MTP K=2）**：接受率 44.0%→40.1%（小头候选域生效的证据），但每步时间纹丝不动（28.2→28.3ms）→ **证伪"draft 采样读全尺寸 output head（2.54GB/次）是大头"假设**。每步成本大头不是带宽，是 kernel 链固定开销。
3. **温度/语言对照**：T=0.7→T=0 接受率 32–44%→44.0%；zh→en 对 MTP 几乎无差（44→45.9%）→ 低接受率是二阶因素，语言对 MTP 无影响。

**结论：每步成本结构 = 裸步 14.7ms + 投机链固定 ~6.7ms + 边际 ~7ms/draft**。固定+边际开销的构成（源码实证）：每轮一次 `device.synchronize()`（program_impl.h:11973/12168）+ host egress 读回校验（11983-11997）+ draft 递归 kernel 链（mtp_impl.h:169-185）+ mtp_pack/mtp_round 打包核。Windows WDDM 模式下 launch/sync 开销显著高于 Linux，放大这些固定成本；裸步本身也带 ~2.1x 低效系数（理论 7ms vs 实测 14.7ms，同一放大机制）。

**作者 96.7–130.8 t/s 的反推**：接受率 59.4% → 产出 2.19 token/步 → 作者每步成本须 16.7–22.6ms（1.0–1.35×裸步）才能成立；我们同代码每步 28.2ms（1.92×）——**差距主因是环境（Windows WDDM launch/sync 开销 + sm_89 路径非原生特化跑 120a），次因是接受率差 14pp**。作者树的 DFlash2 Full 头配置本身就崩（248077 vs 248320 版本裂缝）也旁证论文数字的配置口径与发布树默认不同。

**修订后的实用档位建议**：
- 中文日常：**MTP K=1（72 t/s，+6%）或裸跑（68）**——K=2 及以上无意义
- 英文任务：**DFlash2 K=7 + --lm-head-draft（104.7 t/s，+58%）**不变
- 日常档 BAT 可把 `--draft-tokens 2` 改为 `1`（待用户批准）

### 4.5【情报对齐】作者发布仓库（shensanshu/ninfer-ada-ternary）与我们的差距定位

2026-09-22 用户提供作者 ModelScope 仓库，通读 README + docs/01 + docs/04 后对齐结论：

1. **同源确认**：作者基线 = `Ambolio/ninfer-4090-windows@6eb70a07`（我们 M4 同一棵）；`patches/changed-files` 与我们已铺补丁字节级一致（抽查 `ternary_rowsplit_mma_small_t.cuh`=20522B、`gemm.cu`=8850B、`gemm.cuh`=5464B 全同，作者 09-21 晚的 small-T mma 提交我们早已包含）。**补丁无版本差，排除。**
2. **作者草稿解法四步**（README ★节）：Bonsai 三元无 MTP 头 → 借 Qwen3.8-27B 原版 NextN 层（关键前提：MTP 块不做 Hadamard 旋转，残差流在原始基，可直接借）→ 按 NInfer 规格拼装 + W8G32 量化（12/12 余弦 ≥0.99966 数值精确）→ K=2 最优。**我们 M3 制品正是这个思路的产物，已复现。**
3. **接受率无显著差距**：作者明示强任务依赖（中文短答 80%、英文代码 40.8%、说明文 71→120 token 时 66.7%→54.8%）；我们 zh 作文 256 token 44.0% / en 45.9% 落在其长度效应曲线的合理延伸上。K=3/4/5 崩（40.9/33.2/22.9%）与我们 K 边际分析一致；`--lm-head-draft` 被作者否掉（说明文 63.5%→55.0%）与我们小头实验互证；DFlash 定性"负优化除非重训"与我们 DFlash2 中文 5.4% 互证。
4. **真正差距仍在每轮成本**：作者（4080S sm_89 原生、fp8 KV、131K ctx）MTP 轮 ≈ 裸步 1.07–1.39x → 96.7–130.8 t/s；我们（5080 sm_120a 移植、bf16 KV、32K ctx）1.92x → 68.1 t/s。归因候选：①sm_89 优化 kernel 跑在 120a 上未原生调优（最可疑）；②fp8 vs bf16 KV；③环境（32GB 魔改 4080S、驱动 616.56）。
5. **新操作性情报**：作者 serve 配置含 `--max-concurrency 2`（引擎默认 1，Agent 并发场景必须显式设）；思维链在 `reasoning_content` 字段（客户端只读 `content` 会看到空白——解释了 M6 烟测"空回复"现象）。
6. **待批实验**：fp8 KV 对照（`--kv-dtype fp8 --spec mtp --draft-tokens 2`）——若每轮成本显著下降则 KV dtype 是主因之一，日常档可考虑换 fp8（作者 131K fp8 实用在用）；BAT 补 `--max-concurrency 2`。
