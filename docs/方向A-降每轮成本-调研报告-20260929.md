# 方向A 调研报告：降每轮成本（verify 核 + WDDM ping-pong）

**日期**: 2026-09-29
**范围**: 研究 only（不动代码）；对象：Bonsai-27B-NInfer @ 5080（sm_120a）投机解码每轮成本
**决策背景**: 用户三问答复 = ① 混（中/英混写）② 上下文长度暂缓 ③ 选方向A（降每轮成本）
**硬约束**: 只调研落盘报告，不动代码
**前置**: M6 速度标定报告、项目构建史、上游AB移植验证报告

## 0. TL;DR（结论先行）

**每轮成本 = 裸步 14.7ms + 投机链固定 ~6.7ms/轮 + 边际 ~7ms/draft**（M6 成本模型，实测多源交叉吻合）。

方向A 拆成两个子杠杆：

| 子杠杆 | 本质 | 杠杆性质 | 当前判定 |
|---|---|---|---|
| **(a) verify 核** | ALU/issue-bound（作者 NCU 实证） | 微优化无解；作者指出的杠杆 = 升 K | 任务强相关（接受率随 K 崩）；当前低接受率任务 K=1 是 sweet spot |
| **(b) WDDM ping-pong** | 6.7ms/轮固定 = WDDM launch/sync + sm_89→120a 未原生调优 | 最直接的"降每轮成本"杠杆 | **推荐优先**：降固定开销，能同时救 K=1 并把 K=2/3 推回盈利区 |

**一句话**：verify 核本身（issue-bound）不是能靠微优化降成本的点；真正的"降每轮成本"在 **WDDM 固定开销（6.7ms/轮）** 与 **sm_120a 原生调优**（二者同源，也解释裸步 2.1x）。"升 K"是任务相关的次级杠杆，需先补接受率数据。

## 1. 每轮成本分解（成本模型 + 源码实证）

### 1.1 成本模型（M6 实测）

| 配置 | 接受率(T=0) | 产出/步 | 每步时间 | 吞吐 | vs 裸 |
|---|---|---|---|---|---|
| 裸 | — | 1.00 | 14.7ms | 68.0 | 1.00x |
| MTP K=1 | 54.4% | 1.55 | 21.4ms | **72.0** | **1.06x** |
| MTP K=2 | 44.0% | 1.92 | 28.2ms | 68.1 | 1.00x |
| MTP K=2 + 小头 | 40.1% | 1.79 | 28.3ms | 62.9 | 0.92x |
| DFlash2 K=7 (en) | 21.1% | 2.50 | 23.4ms | 104.7 | 1.58x |
| DFlash2 K=7 (zh) | 5.4% | 1.38 | 21.9ms | 62.0 | 0.91x |

- **判决实验**：K=1 72.0 t/s（54.4%）首次正收益；K=1→K=2 边际 ~7ms/draft 但边际产出仅 0.37 token → **由赚转亏的临界点在 K=1 与 K=2 之间**；K≥3 崩。
- **成本结构**（M6 L108 源码实证）：`裸步 14.7ms + 投机链固定 ~6.7ms + 边际 ~7ms/draft`。
- **固定+边际开销构成**：每轮一次 `device.synchronize()`（program_impl.h:11973/12168）+ host egress 读回校验（11983-11997）+ draft 递归 kernel 链（mtp_impl.h:169-185）+ mtp_pack/mtp_round 打包核。
- **归因**（M6 L110）：**Windows WDDM launch/sync 开销 + sm_89 路径非原生特化跑 120a**；裸步本身带 ~2.1x 低效（理论 7ms vs 实测 14.7ms，同一放大机制）。

### 1.2 关键事实：裸步 2.1x 与投机 6.7ms 是"同一放大机制"

- 理论裸步 7ms，实测 14.7ms（2.1x）
- 投机链固定 6.7ms/轮
- 两者**同源**（WDDM + sm_89→120a 未原生调优）
- **含义**：降每轮成本 = 同时打 (i) 裸步 2.1x 与 (ii) 6.7ms 固定；一个 sm_120a 原生调优 / WDDM 优化可能同时改善两者。

## 2. 子杠杆 (a)：verify 核（issue-bound ALU）

### 2.1 verify 结构（T = draft + 1）

- MTP K3 → verify T=4；DFlash2 K7 → verify T=8
- **当前默认路径**：`launch_small_t`（tensor-core 小 T 核）
  - 门控：`verify_uses_small_t()`（默认 ON；`NINFER_TERNARY_VERIFY=tile` 才切 SIMT）且 `w.k % 1024 == 0`（kSmallTGroupK = 8*128）
- **备选（A/B arm）**：`launch_pq2_gemv_tile`（SIMT token-tile GEMV）
- **int8 rung（s8）**：仅 T ≥ 33（`kTernaryS8MinTokens=33`）才启用 scratch；与当前 K 无关，不进本路径

### 2.2 作者 NCU 证据（ternary_rowsplit_gemm.cu L400-417，原文摘）

> The speculative verify pass runs T = draft + 1 (2..4 here). The reference tiled kernel wastes five of its eight token slots at that size and needs a 128-thread CTA plus seven barriers per output row, which cost more than the whole decode step it was verifying. The small-tile GEMV reads each weight once for all four tokens instead.
>
> The row-blocked kernel below was measured on this same path and LOST: routing T = 2..4 to it dropped the MTP decode from 43.0 to 32.8 t/s (en) and 57.7 to 43.9 t/s (zh). NCU says why, and the reason rules the whole family out for the verify shape rather than just that one config. On the 248320-row head the tile kernel already sits at 95.47% achieved occupancy, 36 registers and 78% SM throughput -- the ALU pipe ("integer and logic operations") is the top utilizer, 909e6 instructions in 1.70 ms against a 1.32 ms pure-issue floor. It is issue-bound with no occupancy left to buy, so trading registers for fewer loads can only lose: the same head under the row block runs at 63 registers, 65.67% occupancy and 47.95% SM throughput.
>
> The verify pass is nonetheless NOT re-reading weights -- nsys shows one forward pass, 401 launches, against 407 for a T=1 decode step -- so the cost is per-token issue work, not weight traffic. That is why raising the draft count, which amortises the per-group 2-bit decode over more tokens, is the productive lever here; see the plan document.

**解读**：
- verify 是 **issue-bound（ALU/integer）**，不是 memory-bound
- occupancy 已 95.47%，**无余量可换**（换 regs 换 load 只会输：row block 63 regs / 65.67% occ / 47.95% SM）
- **不重读权重**（nsys 401 vs 407 launches）→ 压缩权重 / TMA 对 verify 无效（此前"TMA 是红鲱鱼"的结论在此坐实）
- 作者明确：**升 K 是 productive lever**（摊薄 per-group 2-bit decode）

### 2.3 "升 K"杠杆的约束：接受率随 K 崩（实测）

- MTP：K=1 54.4% → K=2 44.0% → K=3 40.9% → K=4 33.2% → K=5 22.9%（逐位一致）
- **任务强相关**：
  - greedy 作文（256 token）：K=1 54.4%
  - 长上下文 Agent 任务（224K档，K=3）：**70.2%**（区间 58.7-95.7%）
  - 作者画像：中文短答 80%、英文代码 40.8%、说明文随长度 66.7%→54.8%
- **含义**：升 K 对"高接受率任务"（长上下文/Agent）可能有效，对"低接受率任务"（greedy 作文）是负优化。当前 5080 实测：低接受率任务 K=1 是 sweet spot，高接受率任务可试 K=3/4。

### 2.4 判定

- 微优化 verify 核（occupancy/regs/布局）：**无解**（作者已证 issue-bound + 无 occupancy 余量）
- 升 K：**任务相关**，不是普适杠杆；需先按任务补接受率 vs K 曲线，再决定
- 结论：verify 核不是"降每轮成本"的主战场，主战场在 (b)

## 3. 子杠杆 (b)：WDDM ping-pong（6.7ms/轮 + 裸步 2.1x）

### 3.1 每轮 flow（源码级，host↔device ping-pong）

```
host 填 mtp_host_ingress（pinned）[program_impl.h:11927-11950]
  → cudaMemcpyHostToDevice（mtp_impl.h:82）
    → GPU: draft 递归 kernel 链 + verify（mtp_impl.h:169-185）
      → cudaMemcpyDeviceToHost（mtp_impl.h:193）
        → device.synchronize()（program_impl.h:11973）  ← 主机等 GPU
          → host 读 egress + 校验（L11983-11997）+ 更新统计/ledger
```

- ingress/egress 是 **pinned host buffer**（program_impl.h:758-759），size = sizeof(MtpDecodeIngress)+sizeof(MtpDecodeEgress)
- ingress/egress 数据量很小（metadata + licensed tokens），**开销不在 copy size，在 WDDM command stream flush + sync**
- program_impl.h 共 **29 个 `device.synchronize()`**（grep 实测）
- 作者 M6 L108 定性：WDDM 模式下 launch/sync 开销显著高于 Linux，放大固定成本

### 3.2 可操作杠杆（研究层面，不动代码）

1. **nsys/nvprof 拆 6.7ms**：量化 copy vs sync vs flush 各自占比（当前未知，是最大盲区）
2. **sm_120a 原生调优**：sm_89→120a 未原生特化是裸步 2.1x 的主因之一；若能把裸步 14.7ms 拉到 ~7ms，投机固定开销大概率同步下降（同源机制）
3. **减少 sync 次数 / 批量多轮**：29 个 sync 中哪些可合并/消除？（架构层面可行性研究）
4. **重叠 ingress copy 与前一轮 host 处理**：hide copy latency（架构层面）
5. **WDDM command stream / flush 调优**：降低每次 launch/sync 的固定开销（平台层面）

### 3.3 判定

- 这是"降每轮成本"的**最直接杠杆**：6.7ms/轮是纯固定开销，降它不改变接受率
- 与 (a) 互补：(a) 升 K 会升接受率压力，(b) 降固定开销能"救"低 K 的盈利性
- 优先度：**高于 (a)**

## 4. 推荐与下一步（研究 only）

### 4.1 推荐排序

1. **优先 (b)**：降 WDDM 固定开销 + sm_120a 原生调优
   - 实验1（最高价值）：nsys 拆 6.7ms 与裸步 14.7ms 的细分（copy/sync/flush/kernel）
   - 实验2：sm_120a 原生调优对裸步 14.7ms 的影响（目标 ~7ms）
   - 实验3：批量/重叠 copy 的架构可行性（只调研，不实现）
2. **次级 (a)**：升 K 杠杆（任务相关）
   - 先补接受率 vs K 曲线（按任务分桶：长上下文 Agent vs greedy 作文 vs 英文代码）
   - 高接受率任务试 K=3/4/5；低接受率任务确认 K=1
3. **交叉**：(b) 降固定开销后重测 (a) 的 K 曲线 —— 固定开销降了，K=2/3 可能从"白干"变"盈利"

### 4.2 关键未知（需补测）

- 6.7ms 与 14.7ms 的**细分**（copy vs sync vs flush vs kernel）—— 当前最大盲区
- 接受率 vs K 的**任务分桶曲线**（当前只有 greedy 作文 + 224K Agent 两个点）
- sm_120a 原生调优对裸步的**实际提升幅度**

### 4.3 与已有结论的衔接

- TMA 红鲱鱼：坐实（verify 不重读权重）
- 升 K 是作者杠杆：成立，但任务相关，非普适
- K=1 是低接受率任务 sweet spot：成立（72.0 t/s）
- 224K Agent 档 K=3 70.2%：升 K 在高接受率任务有空间
