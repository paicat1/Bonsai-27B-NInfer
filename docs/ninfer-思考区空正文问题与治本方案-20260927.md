## 一、问题现象

serve 日志中偶发出现「思考完、无正文」的空收尾：模型消耗大量思考 token 后直接生成 stop token，**整段输出全是思考过程，没有任何回答正文**。

复现实例（`serve_20260927_111202.log`）：

| req | prompt | output | thinking | 预算 | 正文 | 结束方式 |
|---|---|---|---|---|---|---|
| #59 | 68,975 | 8,588 | 8,588/32,000 | 32,000 | 0（空） | stop token |
| #65 | 80,613 | 18,698 | 18,698/32,000 | 32,000 | 0（空） | stop token |

特征：**思考特别长（>8k）且未用到预算（32,000），模型想完直接发 stop**。同会话其他请求（思考 ≤1,282）均正常输出正文；tool-call 请求均有正文。

**影响**：长等待（1~2 分钟）后无任何结果，浪费 GPU 与时间，对深思考/长上下文场景尤其伤人。

## 二、根因定位（源码证据链）

### 2.1 思考→正文的「正常」切出路径

模型从思考区进入正文区，只有两条合法路径：

1. **模型自己输出「思考结束」控制**：`feed_semantic_thinking` 检测到 `kThinkClose`（frontend.cpp:552）→ `in_reasoning=false`。
2. **思考 token 用尽预算**：frontend.cpp:1175-1179 `model_thinking_tokens == *budget` → `control_pending=true` + 返回 `ApplyTargetControl`，引擎强制注入控制 token 进正文区。

### 2.2 为什么本次没走「强制切正文」路径

```
[EVIDENCE] frontend.cpp:1175  if (in_reasoning && budget && model_thinking_tokens == *budget)
                             → 只有「思考恰好用满预算」才强制切正文
[EVIDENCE] frontend.cpp:1160-1166 思考未用满预算时，模型一旦发 stop token，
                            引擎直接 FinishReason::StopToken 终止，不做正文兜底
```

问题请求思考 8,588 / 18,698 均 **未到预算 32,000**，于是没触发 1175，停在 1160 直接按 stop 收尾 → **空正文**。

### 2.3 引擎已有的「强制切正文」通路（完全可复用）

- [EVIDENCE] frontend.cpp:1178 `ContinuationAction::ApplyTargetControl`
- [EVIDENCE] engine_core.h:1243-1245 `ApplyTargetControl` → `EngineRequestState::ControlReady`
- [EVIDENCE] engine_core.h:1850 `preview_control` + engine_core.h:1868 `append_forced_tokens`
  —— 控制 token 由引擎**强制注入**（`</最后答案>` 等结束思考控制），模型随后在正文区继续 decode。

即：预算用尽时引擎能「强行让模型进入正文区」；缺的是「思考区 stop 时也这么做」。

## 三、可选方案对比

| 方案 | 做法 | 效果 | 代价 |
|---|---|---|---|
| **0（什么都不做）** | 维持现状 | 长思考仍会偶发空收尾 | 每次白烧 1~2 分钟 |
| **A** | 调小思考预算（如 8000） | 用「预算用尽强制切正文」兜底，防空收尾 | **思考深度被硬砍**（≤8000），深思考/系统级任务降质 |
| **B** | `--no-thinking` 关思考 | 彻底绕开，绝不空 | 失去思考能力 |
| **C（推荐，治本）** | 引擎：思考区遇到 stop 时强制切正文区 | 保留思考深度 + 保证思考后必进正文 | 改引擎一处 + 重编 + 验证 |

**关键判断**：问题根源不是「思考太长」，而是「模型想完直接 stop 未进正文区」。A 用「削思考深度」换兜底，对深思考任务不划算；C 保留深度又保证正文，才是对症。

## 四、方案 C 设计

### 4.1 改动点（1 处，极小）

`frontend.cpp` 的 `preview_model` stop 分支（现 L1160-1167）增加一个判断：**思考区（`in_reasoning` 且已启用预算）模型发 stop 时，走 `ApplyTargetControl` 强制进正文区，而不是直接终止**。

伪代码（改动前 → 改动后）：

```cpp
// 改动前（frontend.cpp:1160）：
if (stop_token) {
    if (!impl_->policy.publish_stop_token) { /* 还原 before_state */ }
    terminalize(...);
    return complete(count, FinishReason::StopToken);
}

// 改动后：
if (stop_token) {
    if (impl_->preview_semantic.in_reasoning && impl_->preview_semantic.budget) {
        // 方案 C：思考区模型想直接 stop → 强制注入控制 token 进正文区，防空收尾
        impl_->preview_semantic.control_pending = true;
        return complete(count, FinishReason::None,
                        runtime::ContinuationAction::ApplyTargetControl);
    }
    if (!impl_->policy.publish_stop_token) { /* 原有逻辑 */ }
    terminalize(impl_->preview_state, impl_->policy, impl_->preview_output, count);
    return complete(count, FinishReason::StopToken);
}
```

### 4.2 生效流程（复用既有通路）

```
模型思考区发 stop
  → preview_model 拦截（in_reasoning=true）
  → 返回 ApplyTargetControl
  → 引擎设 ControlReady（engine_core.h:1243）
  → preview_control + append_forced_tokens 强制注入「思考结束控制」token
  → feed_semantic_thinking 检测到 kThinkClose → in_reasoning=false
  → 模型在正文区继续生成
```

### 4.3 对既有行为的保护

| 场景 | in_reasoning | 是否受影响 |
|---|---|---|
| 正文区（正常回答）stop | false | 不受影响，照常收尾 |
| 未开思考（budget 无值） | false | 不受影响 |
| 思考正常关闭后 stop | false（已关闭） | 不受影响 |
| 思考区 stop（目标场景） | true | 被拦截，强制进正文区 |

`in_reasoning` 的定义见 frontend.cpp:977 `starts_in_reasoning && thinking.budget.has_value()`，故条件仅在思考启用时成立。

## 五、风险与边界

| 风险 | 描述 | 处置 |
|---|---|---|
| 二次空收尾 | 进正文区后模型第一 token 又 stop | 概率大幅下降；若再发生需二次兜底（暂不启用，避免过度复杂） |
| 容量校验 | 思考预算后的输出容量需容纳控制 token + 一个正文 token | 复用 `validate_generation_capacity`（frontend.cpp:1253）既有保护 |
| 测试回归 | 可能影响 frontend/engine 单元测试 | 实施时重编 + 跑测试 |
| 行为语义 | 原本「思考区 stop」= 结束，改为「思考区 stop」= 进正文 | 需在文档/serve 行为上注明（只对 enabled 思考请求生效） |
| **合法 stop 被强制续写（2026-10-07 补记，据第三方审核报告 D9）** | 新分支在 `in_reasoning && budget` 下**拦截所有 stop**——**包括模型自然收尾的合法 stop**——并强制注入控制 token 续写，故可能**多生成一段** | 属"换取必进正文"的有意权衡；**当前证据仅"78 请求无空收尾"**（未单列该副作用）；若要区分"自然收尾 vs 异常 stop"需另加判据（**当前未做**） |

## 七、结论与建议

- **现状**：这是引擎对「思考区 stop 未进正文」未兜底导致的行为，非崩溃/故障。
- **推荐**：方案 C 治本，改动最小（1 处）、完全复用现有 `ApplyTargetControl` 通路、不牺牲思考深度；最适合深思考/系统级代码场景。
- **替代**：若近期无法改引擎，可用方案 A（把思考预算降到 8000）临时兜底，但会削思考深度，深思考任务不建议。
